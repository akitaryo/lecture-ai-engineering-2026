- 取り組んだレベル：基礎 / 実装 / 発展

- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
【基礎】
config.pyのRAG_TOP_Kを5→2に変更し、ベクトル化された質問の上位の検索数を少なくした。
【実装】
app/retrieval.pyにneighbor_context()を導入し
・検索結果へ同一資料の前後1ページを追加し、別資料のページへまたがない、コンテキスト内でページを重複排除するよう改良した。
・search()においても、contextフィールドにも本文付きページ情報を追加し、通常検索とGraph検索の両方へ反映した。
【発展】
章をまたぐ説明を可能にするため、app/retrieval.pyのbrowse_tree()を次のように改良した。
・資料のページ取得時に、前後ページの context を追加するようにし、章取得時にも前後の neighbor_sections を追加するようにした。
・候補文を最大2文まで返すよう変更した。

- 比較した質問と、固定した条件（モデル・対象資料など）：
比較した質問 : 
"第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？"
"コンパクションとセッションをまたぐメモリの違いは？日々のメモは全部長期メモリになる？"
固定した条件 : 
モデルはgemini-3.5-flash-liteに固定。

- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
【基礎】
検索量とコンテキストが減ったためか、回答生成時間が短くなり、入力トークン数と推定コストが減小した。
一方で、"コンパクションとセッションをまたぐメモリの違いは？日々のメモは全部長期メモリになる？"のような、広範な根拠検索が必要となる質問への回答に対しては、RAG_TOP_K = 5の場合より取得したページ数が不足した。
【実装】
回答において、下記のような"目次を開く"出力が追加された。
[目次を開く] AIエンジニアリング実践講座2026 資料 → 基盤モデルの仕組み → 選んだモデルを、いつ・どう直すか → LoRA と QLoRA ：大きなモデルも GPU 1 台で調整できる（末端ページ・本文717文字を取得）
【発展】
ページの取得時に同じ資料の前後ページがcontextとしてまとまって返り、章を選ぶとneighbor_sectionsで前後の章も確認できるようになった。また、目次ノードにはbreadcrumbと章・ページ数を付けたため、どの講義・章から得た情報かを確認しやすくなった。一方で、候補文を最大2文まで返すよう変更したため、入力Tokenは約3倍、回答時間や推定コストは約2倍になった。

- 改善した例と、残る失敗・制約：
"コンパクションとセッションをまたぐメモリの違いは？日々のメモは全部長期メモリになる？"のような、より広範な資料の探索を必要とする質問に対しても、改良されたTreeを用いれば、複数のモデル応答によって、必要な根拠を網羅的に探索できるようになり、回答が改善した。
一方で、APIの推定コストやモデル応答の回数は増大したので、参照する資料の検索範囲に予め当たりをつけ入力として情報を渡せる機能があるとより効率的な検索に繋がると思った。
